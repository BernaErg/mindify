# Mindify

Self-paced therapeutic parenting training. Static front end, Supabase for accounts
and progress, Netlify for hosting. → **mindify.co.uk**

---

## Deploy it (about 15 minutes, start to finish)

### 1 · Push to GitHub

The repo is already initialised with a commit history. Create an **empty** repo on
GitHub (no README, no .gitignore — it'll conflict), then:

```bash
cd mindify
git remote add origin https://github.com/YOUR-USERNAME/mindify.git
git branch -M main
git push -u origin main
```

### 2 · Connect Netlify

1. netlify.com → **Add new site → Import an existing project → GitHub**
2. Pick the `mindify` repo.
3. Netlify reads `netlify.toml`, so the build settings fill themselves in:
   - Build command: `bash build.sh`
   - Publish directory: `.`
4. **Deploy site.**

It is now live in demo mode. Everything works — you just don't have real accounts yet.

### 3 · Turn on real accounts (Supabase)

1. supabase.com → **New project**. Pick the London (`eu-west-2`) region so student
   data stays in the UK. Free tier is plenty for launch.
2. **SQL Editor → New query** → paste the whole of `supabase/schema.sql` → **Run**.
   That creates the `profiles` and `progress` tables with row-level security, so
   one student can never read another's data.
3. **Project Settings → API** → copy the **Project URL** and the **anon public** key.
4. **Authentication → Providers → Email**: leave *Confirm email* on for production.
   Turn it off while testing so you don't wait for emails.
5. **Authentication → URL Configuration**: set Site URL to your Netlify URL (and
   later `https://mindify.co.uk`), and add `/login.html` to Redirect URLs.
6. Back in Netlify → **Site configuration → Environment variables** → add:

   | Key | Value |
   |---|---|
   | `SUPABASE_URL` | `https://xxxx.supabase.co` |
   | `SUPABASE_ANON_KEY` | `eyJhbGciOi...` |

7. **Deploys → Trigger deploy → Clear cache and deploy site.**

The demo-mode banner disappears and accounts are real. The anon key is *meant* to
be public — RLS in the database is what protects the data, not the key.

### 4 · Custom domain

Netlify → **Domain management → Add a domain** → `mindify.co.uk`. Point your
registrar's nameservers at Netlify, or add the CNAME they give you. HTTPS is
automatic. Then update Supabase's Site URL to match.

## Running it locally

```bash
npm run dev      # builds pages, serves on http://localhost:5173
npm run check    # link + DOM-contract check (run before every push)
```

No dependencies to install. `npm run dev` fetches `serve` on the fly.

## How it's put together

```
index.html  about.html  courses.html  contact.html   ← public site
module.html                                          ← module detail (?m=1..6)
login.html  dashboard.html                           ← student area
privacy.html  terms.html  logos.html                 ← legal + brand sheet

assets/css/styles.css      one design system, CSS variables at the top
assets/js/data.js          ★ all course + testimonial content lives here
assets/js/auth.js          auth/progress layer — Supabase or demo, one API
assets/js/config.js        generated by build.sh, never edit by hand
assets/js/certificate.js   vector PDF certificate (jsPDF)
assets/js/{login,dashboard,module-page,contact,main}.js

tools/layout.js            header, footer, <head> — shared chrome
tools/build-pages.js       public pages
tools/build-portal.js      login, dashboard, legal
tools/check.js             the pre-push sanity check

supabase/schema.sql        run once in the Supabase SQL editor
build.sh                   Netlify build: regenerate pages + inject env vars
```

### The visual system

Everything visual is generated at build time from **`tools/art.js`** — the hero, every
course cover, the section banners and the logo itself, all from the Strata mark's own
geometry. There are no image files to manage and nothing to upload.

Adding a course means adding it to `assets/js/data.js` and running `npm run build`.
Its cover generates itself from the module number, cycling four compositions so two
identical covers never sit next to each other.

The mark ships as **four drawings, not one**. Strata is a filled disc, so it vanishes
on a dark ground, and its three layers close into a blob below about 22px:

| Context | Function |
|---|---|
| Light grounds | `MARK()` |
| Dark grounds  | `MARK_ON_DARK()` |
| Under 22px    | simplified two-layer version (see `/brand`) |
| App icon      | rounded tile (see `/brand`) |

The live brand sheet is at **`/brand`** — mark variants, palette with contrast notes,
image language and type. Send that link to anyone who needs to make something.

Two ambers, deliberately: `--amber` (#D99A3E) is for fills and fails contrast as text;
`--amber-ink` (#9E6420) is the text-safe tone. Every pairing on the site meets WCAG AA.

### Editing content

Almost everything you'll want to change is in **`assets/js/data.js`**:

- `MINDIFY_PLATFORM` — the promise line and the four audience segments, in priority
  order. Psychology students first; that ordering drives copy across the site.
- `MINDIFY_COURSES` — the catalogue. Each course carries `status`
  (`"available"` or `"in-development"`), `level`, `hours`, `summary`, `why`, and
  either a `modules` array or an `outline` array.
- `MINDIFY_TESTIMONIALS` — placeholder quotes. Replace before launch.

Adding a course means adding an object here and running `npm run build`. The
catalogue page, the home preview, the course detail page, the cover art and the
dashboard all pick it up. Nothing else needs editing.

Three of the four courses are **placeholders** marked `in-development` — they exist
so the platform structure is visible. Replace their titles, summaries and outlines
with real ones, then flip `status` to `"available"` and add a `modules` array.

Page copy and layout live in `tools/build-pages.js` / `tools/build-portal.js`.
Edit those and run `npm run build`. **Don't hand-edit the generated `.html` files** —
the next build will overwrite them.

Header, footer and nav are in `tools/layout.js`. One edit, every page.

### The two backends

`assets/js/auth.js` exposes one API (`signUp`, `signIn`, `getProgress`,
`setModuleComplete`, `requireUser`) with two implementations behind it:

- **supabase** — when `SUPABASE_URL` + `SUPABASE_ANON_KEY` are present at build time
- **demo** — otherwise; accounts and progress in `localStorage`, this browser only

Demo mode exists so the site is never broken while you're still setting things up.
It is **not secure** and is clearly labelled as such in the UI. Don't take real
student sign-ups until step 3 above is done.

### The certificate

`assets/js/certificate.js` draws an A4 landscape PDF as vectors (no screenshot, no
image) — crisp at any zoom, ~30KB. It unlocks only when all six modules are ticked.
Each certificate carries a deterministic reference (`MDF-XXXXXXX`) derived from name
+ course + date, so a re-download reproduces the same reference.

Note the honest limitation: the unlock is enforced in the browser, and progress is
self-reported. Someone determined could tick all six without reading anything. If
the certificate ever needs to be tamper-proof, the next step is a Netlify Function
that checks the six rows server-side and signs the PDF. Deliberately out of scope
for this draft.

### Contact form

Wired to **Netlify Forms** — no backend, no third-party service. Submissions appear
under Netlify → **Forms**. Set up a notification email there
(Forms → Settings → Form notifications) or nothing will reach your inbox.

## Known gaps in this draft

Listed plainly so nothing surprises you later:

1. **No lesson content yet.** Module pages show outcomes and key ideas; the teaching
   blocks themselves are still in the PowerPoints. That was the agreed scope.
1b. **Three placeholder courses.** `developmental-neuroscience`, `attachment-in-practice`
   and `psychology-at-work` are outlines only, clearly labelled "In development" on the
   site. Replace or delete them before launch.
2. **No payment.** Enrolment is free. Stripe + a Netlify Function is the usual next step.
3. **No quizzes.** Completion is self-reported ticking.
4. **Testimonials are written placeholders.** Replace them in `data.js` before launch —
   inventing student quotes is a real problem under UK advertising rules (CAP Code),
   not just a bad look.
5. **Legal pages are drafts.** `privacy.html` and `terms.html` are a starting point,
   not solicitor-reviewed. Get them checked before you take money or store real
   children's data.
6. **No email on enrolment.** Supabase sends confirmation and reset emails; there's
   no welcome sequence.
7. **Certificate names are Latin-only.** jsPDF's built-in fonts are WinAnsi-encoded.
   Accents (ü ö ç é) print exactly as typed; Turkish ğ ş ı are transliterated;
   Cyrillic, Greek and CJK names come out as `?`. Fixing that properly means
   embedding a Unicode font (~300KB) — worth doing only if you get students who
   need it.

## Verification

`npm run check` validates every internal link and the DOM contracts the page
scripts depend on. Beyond that, the following were tested before handover:
the full demo-mode flow (sign up → wrong password rejected → sign in → tick
modules → certificate locked at 2/6, unlocked at 6/6 → PDF downloads), account
isolation (one student can't see another's progress), certificate rendering with
Turkish, accented, very long and non-Latin names, and `build.sh` in both demo and
Supabase-configured modes.

Two things were deliberately *not* verified because there's no browser in the
build environment: how it looks in Safari/Chrome on a real phone, and Supabase in
live mode. Open it on your phone and run through sign-up once before you show
anyone.

## Brand

`logos.html` (also at `/logos`) is the brand sheet: four logo directions, each shown
as a lockup on light and dark, stacked, and at four sizes down to 16px. Source SVGs
are in `assets/logos/`. All use `currentColor`, so one CSS variable recolours them.

Fonts: **Fraunces** (headings) and **Inter** (body), both open source, both free.
